# Windows 11 Enterprise + WSL 2 + .NET 10 + Testcontainers

_Research snapshot: 20 September 2026. Scope: Docker Engine installed inside Ubuntu on WSL 2, not Docker Desktop. Sources are first-party documentation and upstream project repositories._

## Executive recommendation

Use a **Linux-native development lane inside WSL 2**: Ubuntu LTS, the .NET 10 SDK, the Docker Engine daemon, the repository, `dotnet test`, and Testcontainers should all run inside the same Ubuntu distribution. Edit through a WSL-aware IDE integration, but do not run the Windows .NET SDK against a Docker Unix socket in WSL. This keeps the normal Linux Docker socket (`/var/run/docker.sock`), Testcontainers auto-discovery, bind paths, port mappings, and CI behavior aligned without exposing the Docker API over TCP. WSL 2 provides the full Linux-kernel system-call compatibility needed by Docker, while Testcontainers for .NET requires a Docker-API-compatible runtime and auto-detects recent Docker on Linux. ([Microsoft: compare WSL versions](https://learn.microsoft.com/en-us/windows/wsl/compare-versions), [Testcontainers system requirements](https://dotnet.testcontainers.org/))

The sensible distro choices are:

- **Ubuntu 24.04 LTS** for the more established baseline. It is supported by Docker Engine, has .NET 10 in Ubuntu's built-in feed, and receives standard Ubuntu security maintenance through May 2029. ([Docker Engine on Ubuntu](https://docs.docker.com/engine/install/ubuntu/), [Microsoft: install .NET on Ubuntu](https://learn.microsoft.com/en-us/dotnet/core/install/linux-ubuntu-install), [Canonical: Ubuntu release cycle](https://ubuntu.com/about/release-cycle?product=ubuntu&release=ubuntu&version=24.04+LTS))
- **Ubuntu 26.04 LTS** for the longest current runway. It is now also listed as supported by Docker Engine and supplies .NET 10 from Ubuntu's built-in feed. Its relative newness may matter to enterprise qualification, so make this an explicit platform-owner decision rather than silently following the unversioned `Ubuntu` WSL alias. ([Docker Engine on Ubuntu](https://docs.docker.com/engine/install/ubuntu/), [Microsoft: install .NET on Ubuntu](https://learn.microsoft.com/en-us/dotnet/core/install/linux-ubuntu-install))

Pin the numbered distro (`Ubuntu-24.04` or `Ubuntu-26.04`), the .NET SDK via `global.json`, the Testcontainers NuGet package, and every dependency image tag or digest. .NET 10 is an LTS release supported through 14 November 2028. Testcontainers explicitly recommends pinned image versions and random resource names/ports. ([Microsoft .NET lifecycle](https://learn.microsoft.com/en-ie/lifecycle/products/microsoft-net-and-net-core), [Testcontainers best practices](https://dotnet.testcontainers.org/api/best_practices/))

## Decisions that must be made before provisioning

1. **Which Windows 11 release and WSL servicing channel does enterprise IT support?** Advanced enterprise networking requires Windows 11 22H2 or later and WSL 2.0.9 or later; Store-delivered WSL is Microsoft's recommended enterprise baseline, and policy can disable inbox WSL. ([Microsoft: enterprise WSL setup](https://learn.microsoft.com/en-us/windows/wsl/enterprise), [Microsoft: WSL Intune settings](https://learn.microsoft.com/en-us/windows/wsl/intune))
2. **Which numbered Ubuntu LTS is approved: 24.04 or 26.04?** Both meet current Docker/.NET requirements; 24.04 is the conservative choice, while 26.04 has the longer lifecycle.
3. **Must all builds and tests execute in WSL?** This research recommends yes. A Windows-hosted test process would require cross-boundary Docker connectivity and explicit Testcontainers host/socket configuration, substantially increasing networking and security complexity. Testcontainers supports `DOCKER_HOST`, TLS, certificate paths, socket override, and host override, but those should be escape hatches, not the workstation default. ([Testcontainers custom configuration](https://dotnet.testcontainers.org/custom_configuration/), [Docker: protect daemon access](https://docs.docker.com/engine/security/protect-access/))
4. **Does policy permit rootful Docker socket access?** Membership in the `docker` group grants root-level privileges. Rootless Docker reduces daemon privilege but has networking, AppArmor, and cgroup/resource-control limitations and is a higher compatibility risk because Testcontainers' Ryuk resource reaper defaults to privileged mode. ([Docker Linux post-install](https://docs.docker.com/engine/install/linux-postinstall/), [Docker rootless limitations](https://docs.docker.com/engine/security/rootless/troubleshoot/), [Testcontainers custom configuration](https://dotnet.testcontainers.org/custom_configuration/))
5. **What are the proxy, TLS interception, private-registry, and egress rules?** WSL, Ubuntu APT, NuGet, Docker's APT repository, the Docker daemon, Docker/other registries, and processes inside test containers are distinct trust/proxy surfaces; Windows proxy and certificate settings do not by themselves solve all of them. ([Microsoft: WSL networking](https://learn.microsoft.com/en-us/windows/wsl/networking), [Docker daemon proxy](https://docs.docker.com/engine/daemon/proxy/), [Docker CA certificates](https://docs.docker.com/engine/network/ca-certs/))
6. **Which Linux container images and registries are permitted?** Testcontainers pulls a Ryuk image plus dependency images unless mirrored/substituted. Its configuration supports a registry-prefix substitution, Docker auth configuration, and a custom Ryuk image. ([Testcontainers custom configuration](https://dotnet.testcontainers.org/custom_configuration/))
7. **What CI platform and runner OS will be authoritative?** For parity, use an x64 Linux runner with Docker and the same SDK/package/image pins. Testcontainers needs Docker locally or remotely; hosted Windows agents use the Windows engine and cannot run Linux containers. ([Testcontainers CI guidance](https://dotnet.testcontainers.org/cicd/))

## Supported baseline and prerequisites

### Windows and WSL

- Windows 11 satisfies the WSL 2 OS requirement, but hardware virtualization must be enabled and the Windows `VirtualMachinePlatform`/WSL components must be permitted. `wsl --install` enables the required components, installs a kernel, sets WSL 2 as default, and installs Ubuntu; enterprise policy may instead require a managed or offline path. ([Microsoft: install WSL](https://learn.microsoft.com/en-us/windows/wsl/install), [Microsoft: manual WSL installation](https://learn.microsoft.com/en-us/windows/wsl/install-manual))
- Prefer current Store WSL rather than the legacy inbox component so that systemd and enterprise controls are available on the documented cadence. Enterprises can control WSL, WSL 1, disk mounting, debug shell, custom kernels, networking, firewall, and other `.wslconfig` settings through Intune or the WSL ADMX policy. ([Microsoft: WSL configuration/systemd](https://learn.microsoft.com/en-us/windows/wsl/wsl-config), [Microsoft: WSL Intune settings](https://learn.microsoft.com/en-us/windows/wsl/intune))
- If Microsoft Store access is blocked, Microsoft documents direct distribution download and manual installation, while Canonical publishes numbered `.wsl` images that can be installed with `wsl --install --from-file`; Ubuntu's new tar-based WSL format requires WSL 2.4.10 or later. ([Microsoft: manual WSL distribution installation](https://learn.microsoft.com/en-us/windows/wsl/install-manual), [Canonical: install Ubuntu on WSL 2](https://documentation.ubuntu.com/wsl/latest/guides/install-ubuntu-wsl2/))
- Record and enforce the outputs of `winver`, `wsl --version`, `wsl --status`, and `wsl --list --verbose`; a distro must report version `2`, not `1`. These are the supported WSL inspection commands. ([Microsoft: basic WSL commands](https://learn.microsoft.com/en-us/windows/wsl/basic-commands))

### Ubuntu and .NET 10

- Docker currently supports 64-bit Ubuntu 22.04, 24.04, and 26.04 LTS. Use Docker's signed APT repository and install `docker-ce`, `docker-ce-cli`, `containerd.io`, Buildx, and the Compose plugin; Docker warns to remove conflicting distro packages first. ([Docker Engine on Ubuntu](https://docs.docker.com/engine/install/ubuntu/))
- Ubuntu 24.04 and 26.04 both provide `dotnet-sdk-10.0` through the built-in Ubuntu feed. Avoid mixing Microsoft and Ubuntu .NET feeds because Microsoft explicitly warns about package mix-ups. ([Microsoft: install .NET on Ubuntu](https://learn.microsoft.com/en-us/dotnet/core/install/linux-ubuntu-install))
- Put a `global.json` in each repository to select an approved .NET 10 SDK feature band and roll-forward policy, rather than accepting whichever SDK APT last installed. `global.json` controls SDK selection independently of the target runtime. ([Microsoft: `global.json` overview](https://learn.microsoft.com/en-us/dotnet/core/tools/global-json))

### systemd, cgroups, and daemon lifecycle

- Run Docker as a systemd-managed service. Current Ubuntu distributions run systemd by default in recent WSL; if it is not active, `/etc/wsl.conf` supports `[boot] systemd=true`, followed by `wsl --shutdown`. Verify systemd rather than assuming it from the Ubuntu release. ([Microsoft: WSL systemd](https://learn.microsoft.com/en-us/windows/wsl/systemd), [Microsoft: WSL configuration](https://learn.microsoft.com/en-us/windows/wsl/wsl-config))
- Docker's Ubuntu packages use systemd and the service normally starts with the distro. Validate `systemctl is-active docker`, `docker version`, `docker info`, and `docker run --rm hello-world`. A WSL distribution still has to start before its Linux services exist; do not treat it as an always-on Windows service. ([Docker Engine on Ubuntu](https://docs.docker.com/engine/install/ubuntu/))
- Check `docker info` for the cgroup driver/version and verify actual CPU/memory limits in a smoke test. This matters especially if rootless mode is chosen: Docker documents cgroup resource flags as supported only with cgroup v2 and systemd in rootless mode, with controller delegation caveats. ([Docker rootless tips](https://docs.docker.com/engine/security/rootless/tips/))

## Filesystem and resource layout

- Keep repositories, NuGet caches, build output, Testcontainers bind sources, and Docker data on the WSL ext4 filesystem (for example `~/src`), not `/mnt/c`. Microsoft recommends storing files in the same OS filesystem as the tools and warns that cross-OS access is slower. ([Microsoft: working across WSL filesystems](https://learn.microsoft.com/en-us/windows/wsl/filesystems), [Microsoft: compare WSL versions](https://learn.microsoft.com/en-us/windows/wsl/compare-versions))
- Keep Docker's data root on the Linux filesystem. Native Linux Engine defaults to `/var/lib/docker`; fresh Docker Engine 29+ installations using the containerd image store also place image contents/snapshots under `/var/lib/containerd`. Moving `data-root` does not move containerd's snapshot store, so disk design must account for both. ([Docker daemon configuration](https://docs.docker.com/engine/daemon/))
- On a 64-GB laptop, WSL's documented defaults are 50% of Windows RAM and all logical processors, with swap equal to 25% of Windows RAM rounded up. Do not automatically allocate all 64 GB: establish an initial organization-approved cap after measuring the application and its heaviest test suite, leaving capacity for Windows security, IDE, browser, and collaboration tools. `.wslconfig` is global to all WSL 2 distributions, and changes may require `wsl --shutdown`. ([Microsoft: WSL advanced settings](https://learn.microsoft.com/en-us/windows/wsl/wsl-config))
- Control disk growth: Docker's default `json-file` logging has no rotation and can exhaust disk; Docker recommends the `local` logging driver to prevent this. Define cache/image cleanup policy without pruning resources during active parallel tests. ([Docker logging drivers](https://docs.docker.com/engine/logging/configure/))

## Networking and localhost behavior

- Run test processes in WSL with the daemon. Container ports published by Docker are then reached from the same Linux test host, avoiding Windows-to-WSL discovery. In test code, follow Testcontainers guidance: request random host ports, read the mapped port, use the container's `Hostname` rather than hard-coding `localhost`, and use network aliases for container-to-container communication. ([Testcontainers best practices](https://dotnet.testcontainers.org/api/best_practices/))
- WSL defaults to NAT. Windows can normally access Linux services through `localhost`, but WSL-to-Windows access under NAT uses the Windows host address. Windows 11 22H2+ supports mirrored networking, which permits bidirectional IPv4 localhost, improves VPN compatibility, adds IPv6/multicast, and applies Hyper-V firewall behavior; WSL 2.0.9+ enables Hyper-V firewall integration by default. ([Microsoft: WSL networking](https://learn.microsoft.com/en-us/windows/wsl/networking))
- Do not mandate mirrored networking without a corporate VPN/firewall pilot. Microsoft documents WSL/Docker issues in the mirrored mode troubleshooting section, while Intune may forbid users from changing `networkingMode`. Begin with NAT unless a real VPN/DNS/localhost requirement justifies mirrored mode, then test container port publishing, DNS, registry access, and Hyper-V firewall policy on the enterprise image. ([Microsoft: WSL troubleshooting](https://learn.microsoft.com/en-us/windows/wsl/troubleshooting), [Microsoft: WSL Intune settings](https://learn.microsoft.com/en-us/windows/wsl/intune))
- Docker-published ports can bypass `ufw`/`firewalld` rules, and Docker supports `iptables-nft` or `iptables-legacy`, not raw `nft` rules. Combine Linux `DOCKER-USER` rules with Windows/Hyper-V firewall controls, and bind only what tests need. ([Docker Engine on Ubuntu](https://docs.docker.com/engine/install/ubuntu/), [Microsoft: enterprise WSL setup](https://learn.microsoft.com/en-us/windows/wsl/enterprise))

## Testcontainers for .NET design

- Add the core `Testcontainers` NuGet package or an official dependency module to the integration-test project. Testcontainers supports compatible .NET Standard consumers and a Docker-API-compatible runtime; recent Docker on Linux is an actively tested path. ([Testcontainers for .NET](https://dotnet.testcontainers.org/), [Testcontainers modules](https://dotnet.testcontainers.org/modules/))
- With `dotnet test` running in WSL and the user's Docker CLI already working, rely first on auto-discovery of `/var/run/docker.sock`. Do not set `DOCKER_HOST` unless detection fails or CI uses a remote daemon. Testcontainers can be configured through `~/.testcontainers.properties` or environment variables including `DOCKER_HOST`, `DOCKER_CONTEXT`, TLS/certificate settings, `TESTCONTAINERS_HOST_OVERRIDE`, and `TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE`. ([Testcontainers custom configuration](https://dotnet.testcontainers.org/custom_configuration/))
- Leave Ryuk enabled. It cleans leaked containers, networks, and volumes; disabling it is explicitly discouraged. Its default is a pinned `testcontainers/ryuk` image and privileged execution, which must be approved or accommodated by the enterprise runtime policy. Mirror/substitute this image if direct Docker Hub pulls are not allowed. ([Testcontainers best practices](https://dotnet.testcontainers.org/api/best_practices/), [Testcontainers custom configuration](https://dotnet.testcontainers.org/custom_configuration/))
- Never rely on static container names or fixed host ports: both break parallel developer/CI runs. Use per-test/per-suite lifecycle deliberately, module wait strategies, and asynchronously dispose containers. Prefer resource-copy APIs over host bind mounts to reduce path coupling. ([Testcontainers best practices](https://dotnet.testcontainers.org/api/best_practices/), [Testcontainers wait strategies](https://dotnet.testcontainers.org/api/wait_strategies/))
- Pin the Testcontainers package and follow its releases when upgrading Docker Engine. The upstream project has previously needed explicit Docker API compatibility work for Engine 29, and its current configuration exposes `DOCKER_API_VERSION` with a documented default of `1.44`; validate the chosen package against the approved daemon version in the workstation image and CI. ([Testcontainers releases](https://github.com/testcontainers/testcontainers-dotnet/releases), [Testcontainers custom configuration](https://dotnet.testcontainers.org/custom_configuration/))

## Enterprise proxy, certificate, registry, and security controls

- WSL `autoProxy=true` can import Windows HTTP proxy information; DNS tunneling is enabled by default on Windows 11 22H2+ and is designed for VPN/complex DNS compatibility. These features are policy-controllable and should be tested with authenticated PAC proxies and VPN reconnects. ([Microsoft: WSL networking](https://learn.microsoft.com/en-us/windows/wsl/networking), [Microsoft: WSL advanced settings](https://learn.microsoft.com/en-us/windows/wsl/wsl-config))
- Configure the Docker **daemon** proxy separately (prefer `daemon.json` or a systemd drop-in) and include internal registries in `NO_PROXY`. Shell proxy variables only cover the CLI/process that receives them. ([Docker daemon proxy](https://docs.docker.com/engine/daemon/proxy/))
- Import the corporate CA into Ubuntu's trust store for APT, NuGet, Git, and HTTPS tooling; configure registry-specific CAs under `/etc/docker/certs.d/<registry>/` for rootful Native Linux Engine. Containers that call internal HTTPS services also need that CA in their own image trust store. Docker cautions that MITM roots should be handled with the security team. ([Docker registry certificates](https://docs.docker.com/engine/security/certificates/), [Docker CA certificates](https://docs.docker.com/engine/network/ca-certs/))
- Do not expose the Docker API on unauthenticated TCP/2375. The local Unix socket and `docker` group are root-equivalent; remote access, if unavoidable, needs mutual TLS or SSH and tightly guarded credentials. ([Docker: protect daemon access](https://docs.docker.com/engine/security/protect-access/), [Docker Linux post-install](https://docs.docker.com/engine/install/linux-postinstall/))
- Microsoft recommends enterprise WSL management through Intune, Hyper-V firewall controls, and the Defender for Endpoint WSL plug-in. The plug-in provides WSL event visibility but has documented feature limitations, including lack of antimalware, threat/vulnerability management, and response commands on the WSL logical device; security owners must decide how that affects acceptance. ([Microsoft: enterprise WSL setup](https://learn.microsoft.com/en-us/windows/wsl/enterprise), [Microsoft Defender for Endpoint WSL plug-in](https://learn.microsoft.com/en-us/defender-endpoint/mde-plugin-wsl))
- Installing native Docker Engine avoids Docker Desktop's subscription terms. Docker states that Docker Desktop requires paid entitlement for professional use in larger organizations, while licensing/distribution of open-source Docker/Moby projects such as Docker Engine is unchanged; Docker Engine's install documentation identifies Apache 2.0 licensing. Legal/procurement should still approve the exact packages, registries, and support model. ([Docker Desktop license](https://docs.docker.com/subscription-billing/desktop-license/), [Docker Engine install overview](https://docs.docker.com/engine/install/))

## CI parity

Define one Linux contract for workstation and CI:

- `linux/amd64` unless ARM64 is an explicit supported target;
- .NET 10 SDK pinned by the same `global.json`;
- same Testcontainers package version;
- the same image tags/digests and private-registry substitution;
- Docker Engine versions tested within an approved range;
- identical proxy/CA behavior and no hidden dependency on Windows-only hostnames or paths.

Testcontainers' CI documentation says Docker may be local or remote. Prefer a Linux runner with direct Docker access and Ryuk supported. If CI uses Docker-in-Docker or a remote daemon, explicitly set `DOCKER_HOST` and test cleanup/host resolution; do not copy a CI-specific insecure TCP/2375 setup onto laptops. Hosted Windows agents run Windows containers and cannot substitute for the Linux-container lane. ([Testcontainers CI guidance](https://dotnet.testcontainers.org/cicd/), [Testcontainers custom configuration](https://dotnet.testcontainers.org/custom_configuration/))

## Qualification checklist / acceptance gates

Before calling the workstation image supported, automate or record these checks:

1. Windows/WSL: approved Windows build; `wsl --version` at the enterprise minimum; numbered Ubuntu distro reports WSL version 2; systemd active; WSL policies applied.
2. Toolchain: `dotnet --info` resolves the repository's pinned .NET 10 SDK; package restore works through the enterprise proxy/feed; no mixed .NET package repositories.
3. Runtime: Docker and containerd services active; `docker version`, `docker info`, cgroup details, storage driver, logging driver, and `hello-world` are as approved.
4. Security/network: no daemon TCP listener; group/rootless choice documented; private registry login/pull works; corporate CA works in Ubuntu and a representative test image; VPN connect/disconnect and DNS suffix changes are tested.
5. Testcontainers smoke suite: start two dependency types concurrently, use random ports, resolve readiness, communicate host-to-container and container-to-container, then verify Ryuk cleanup after both normal completion and a forcibly terminated test process.
6. Resource pressure: execute the largest integration-test suite in parallel while measuring WSL memory, Windows memory, swap, CPU, VHD growth, Docker logs, and recovery after `wsl --shutdown`.
7. CI parity: run the identical smoke suite on the authoritative Linux runner using the same SDK, package, and image pins.
8. Recovery/update: prove how to update WSL, Ubuntu security packages, .NET servicing releases, Docker Engine, and Testcontainers independently; test rollback or image rebuild before enterprise-wide rollout.

## Known constraints and residual risks

- Native Docker Engine inside WSL is a Linux installation managed by the organization; Docker says it does not provide support for Docker Engine as a standalone product in the same way it supports its commercial products. Decide who owns workstation-image support and incident triage. ([Docker Engine install overview](https://docs.docker.com/engine/install/))
- WSL 2 is a managed VM. Its `.wslconfig` memory/CPU settings affect all WSL 2 distributions, the VM has a VHD lifecycle, and its networking differs from a native Linux host. Keep the CI Linux lane authoritative for release confidence. ([Microsoft: WSL advanced settings](https://learn.microsoft.com/en-us/windows/wsl/wsl-config), [Microsoft: compare WSL versions](https://learn.microsoft.com/en-us/windows/wsl/compare-versions))
- Rootful Docker is the lowest-friction Testcontainers path but makes Docker access root-equivalent. Rootless mode is not a drop-in compliance fix because its cgroup, networking, storage, AppArmor, and privileged-container behavior differs. ([Docker Linux post-install](https://docs.docker.com/engine/install/linux-postinstall/), [Docker rootless limitations](https://docs.docker.com/engine/security/rootless/troubleshoot/))
- Corporate TLS inspection and authenticated proxies operate at different layers. A successful browser request on Windows does not prove that Ubuntu tooling, the Docker daemon, or dependency containers have the required proxy configuration and CA trust. ([Docker daemon proxy](https://docs.docker.com/engine/daemon/proxy/), [Docker CA certificates](https://docs.docker.com/engine/network/ca-certs/))
- Testcontainers pulls and executes dependency images, including its resource reaper. Image allow-listing, vulnerability scanning, digest pinning, registry mirroring, update cadence, and secret handling are therefore platform-design concerns, not merely test-library configuration. Testcontainers supports image-name substitution and recommends explicit image-version pins. ([Testcontainers custom configuration](https://dotnet.testcontainers.org/custom_configuration/), [Testcontainers best practices](https://dotnet.testcontainers.org/api/best_practices/))

## Questions for the design interview

These answers materially change the implementation:

1. Are developers allowed to enable virtualization/WSL and install Store WSL, or must IT distribute a prebuilt/offline image?
2. Which exact Windows 11 build, WSL version/channel, CPU architecture, Ubuntu LTS, and update rings are approved?
3. Must developers use Visual Studio on Windows, or can build/debug/test execute inside WSL through VS Code/Rider/Visual Studio integration?
4. Does source code have to live on NTFS for backup/DLP, or may it live inside the WSL VHD? How is that VHD backed up, encrypted, scanned, and recovered?
5. Is root-equivalent membership in the Docker group acceptable on a single-user enterprise laptop? If not, will security accept and qualify rootless Docker plus privileged Ryuk, or require a remote managed daemon?
6. Which Testcontainers dependencies are needed (SQL Server, PostgreSQL, Kafka, Service Bus emulator, etc.), how many run concurrently, and what RAM/disk budget does the worst suite require?
7. Are Docker Hub, `mcr.microsoft.com`, NuGet.org, Ubuntu archives, Microsoft package endpoints, and Docker's APT repository reachable, mirrored, or blocked?
8. Is there TLS inspection, an authenticated/PAC proxy, split-tunnel VPN, internal DNS suffixes, or a private CA? Can service accounts/noninteractive processes authenticate?
9. May containers publish ports to Windows/LAN, or must they remain local to WSL? Is mirrored networking allowed by Intune and compatible with the corporate VPN/Hyper-V firewall policy?
10. Which CI product and runner model is authoritative, and can it run Linux Docker with privileged Ryuk? Must tests also support ARM64 or Windows containers?
11. What are the supply-chain requirements for image digests, SBOMs, vulnerability thresholds, registry provenance, and patch SLAs?
12. Who owns support for WSL, Ubuntu, Docker Engine, .NET, Testcontainers, proxy/certificates, and the curated developer image when an update breaks integration tests?
